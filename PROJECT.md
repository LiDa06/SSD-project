## 1. Назначение

Продукт представляет собой небольшой сервис заказов, в котором клиент выбирает товары из каталога, указывает необходимое количество и оформляет заказ. Сервис сохраняет состав и стоимость заказа, связывает заказ с клиентом и отслеживает его состояние от создания до завершения или отмены. Основная предметная логика приложения включает формирование заказа из позиций каталога, серверный расчёт его стоимости и управление состоянием заказа.

## 2. Граница продукта

**В продукт входит:**

- аутентификация пользователей и разграничение действий ролей `Customer` и `Employee`,

- просмотр клиентом доступного каталога товаров;

- создание заказа из выбранных товаров;

- указание количества для каждой позиции заказа;

- расчёт стоимости заказа на сервере;

- сохранение заказа и его позиций;

- привязка заказа к создавшему его клиенту;

- просмотр клиентом своих заказов и их текущих статусов;

- обработка заказов сотрудником;

- изменение статуса заказа в соответствии с допустимыми переходами;

- отмена клиентом собственного заказа в статусе `Created`;

- создание и изменение сотрудником товаров каталога.

**Внешнее окружение и внешние системы:**

- для взаимодействия с REST API могут использоваться браузер, Swagger UI, Postman или иной HTTP-клиент;

- внешние информационные системы и облачные сервисы продукту для выполнения основных сценариев не требуются.

**Команда сознательно не реализует:**

- онлайн-оплату;

- реальную доставку и интеграцию со службами доставки;

- промокоды и бонусные программы;

- сложную CRM;

- интеграцию со сторонними магазинами и внешними каталогами;

- другие внешние интеграции, не необходимые для основных сценариев сервиса.

## 3. Пользователи и доступные действия

Укажите пользователей с различающимися доступными и запрещёнными действиями.

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| Сотрудник (`Employee`) | Пользователь, который ведёт каталог и обрабатывает поступившие заказы | Просматривать заказы в статусе `Created`; принимать заказ в работу; просматривать заказы, назначенные ему; завершать обработку назначенного ему заказа в статусе `Processing`; создавать товары; изменять название, описание, цену и доступность товаров каталога | Создавать и отменять заказы от имени клиентов; завершать заказ, не назначенный ему; переводить заказ в произвольный статус; изменять состав, сохранённые цены и итоговую стоимость уже созданного заказа; получать доступ к учётным данным пользователей |
| Клиент (`Customer`) | Пользователь, который оформляет заказы | Просматривать каталог; выбирать товары и количество; создавать заказ; просматривать собственные заказы и их текущие статусы; отменять собственный заказ в статусе `Created`. | Просматривать или изменять заказы других клиентов; отменять заказ после принятия его в обработку; изменять каталог и цены; переводить заказы в служебные статусы `Processing` и `Completed`. |

## 4. Сквозные сценарии

Опишите два-три законченных сценария. Сценарий начинается с потребности пользователя, включает связанные действия и завершается значимым результатом или изменением состояния системы.

### Сценарий 1. Создание заказа

- **Участники:** Клиент (`Customer`), серверное приложение, база данных.
- **Начальное условие:** Клиент вошёл в систему с ролью `Customer`, в каталоге присутствуют доступные товары.
- **Основные действия:** клиент просматривает каталог, выбирает один или несколько товаров, указывает необходимое количество и отправляет запрос на создание заказа. Сервис получает актуальные данные выбранных товаров, рассчитывает стоимость заказа на сервере и создаёт заказ, принадлежащий текущему клиенту.
- **Результат:** клиент получает созданный заказ со статусом `Created`, содержащий выбранные позиции и рассчитанную стоимость.
- **Какие данные или состояние изменяются:** создаётся объект заказа и его позиции; фиксируются количество и стоимость позиций; заказ связывается с текущим клиентом; заказу устанавливается первоначальный статус `Created`.

### Сценарий 2. Работа с каталогом и стоимостью

- **Участники:** Клиент, сотрудник, серверное приложение, база данных.
- **Начальное условие:** В системе существует каталог товаров. Сотрудник имеет право создавать и изменять позиции каталога, а клиент может просматривать доступные позиции.
- **Основные действия:** Сотрудник создаёт товар или изменяет его название, описание, цену и доступность. Сервер проверяет права сотрудника и сохраняет изменения в каталоге. Клиент просматривает доступные товары и выбирает одну или несколько позиций с указанным количеством. При создании заказа клиент передаёт только идентификаторы товаров и количество. Сервер проверяет существование и доступность выбранных товаров, получает цены из каталога на момент создания заказа, рассчитывает стоимость каждой позиции и итоговую стоимость заказа. Полученные цены сохраняются в `OrderItem`.
- **Результат:** Заказ создан со статусом `Created`; состав заказа, количество, цены позиций и итоговая стоимость зафиксированы на момент оформления. Последующее изменение цены в каталоге не изменяет стоимость уже созданного заказа.
- **Какие данные или состояние изменяются:** При изменении каталога обновляются данные `Product`. При создании заказа создаётся запись `Order` и связанные `OrderItem` с количеством и зафиксированными ценами. Итоговая стоимость `TotalPrice` рассчитывается сервером. Цена, переданная клиентом, не используется.

### Сценарий 3. Обработка заказа сотрудником

- **Участники:** Сотрудник, серверное приложение, база данных.
- **Начальное условие:** Клиент ранее создал заказ; заказ имеет статус `Created`. Сотрудник вошёл в систему с ролью `Employee`.
- **Основные действия:** Сотрудник просматривает доступные для обработки заказы и выбирает заказ со статусом `Created`. Он отправляет команду принять заказ в работу. Сервер проверяет роль сотрудника и текущий статус заказа, назначает сотрудника ответственным и переводит заказ в статус `Processing`. После выполнения обработки сотрудник отправляет команду завершить заказ. Сервер проверяет, что заказ находится в статусе `Processing` и назначен текущему сотруднику, затем переводит его в статус `Completed`.
- **Результат:** Заказ обработан и получает статус `Completed`; клиент может увидеть актуальный статус своего заказа.
- **Какие данные или состояние изменяются:** При принятии заказа сохраняются идентификатор ответственного сотрудника и статус `Processing`. При завершении изменяется статус на `Completed`. После перехода в `Completed` состав заказа, цены позиций и итоговая стоимость не изменяются.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| **Product** (название, описание, цена, доступность) | Клиент, сотрудник | Клиент видит неактуальные условия; возможна подмена цены или доступности | Заказ оформляется по неверной цене; недоступный товар попадает в заказ; ломается расчёт итоговой стоимости |
| **OrderItem** (товар, количество, зафиксированная цена) | Клиент, сотрудник | Раскрытие состава заказа | Изменение состава или цены задним числом искажает заказ; пересчёт итога; спор с клиентом |
| **Цена на момент создания заказа** | Клиент, сотрудник | Раскрытие коммерческих условий | Если не зафиксирована, итог заказа меняется при последующем изменении каталога |
| **Order** (владелец, статус, итоговая стоимость) | Клиент, сотрудник | Раскрытие действий клиента и объёма заказов | Неверный статус приводит к пропуску или повторной обработке; неверная сумма — к спору с клиентом |

## 6. Компоненты и внешние взаимодействия

Продукт состоит из следующих частей:

1. **HTTP-клиент.**  
   Браузерный интерфейс, Swagger UI или иной REST-клиент, через который клиент и сотрудник отправляют запросы к сервису. HTTP-клиент не имеет прямого доступа к базе данных.

2. **Серверное приложение.**  
   REST API на Python с использованием FastAPI. Сервер выполняет аутентификацию пользователей, определяет роль текущего пользователя, проверяет права доступа, обрабатывает команды создания и отмены заказов, обрабатывает команды сотрудника, управляет каталогом, рассчитывает стоимость заказа на стороне сервера и контролирует допустимые переходы состояний заказа.

3. **Реляционная база данных.**  
   PostgreSQL хранит учётные записи пользователей, товары каталога, заказы и позиции заказов. Доступ к базе данных выполняется только серверным приложением.

Основные взаимодействия:

- HTTP-клиент обращается к REST API по HTTP при локальном запуске и по HTTPS при развёртывании;
- при входе пользователь передаёт серверу учётные данные;
- после входа HTTP-клиент передаёт access token в заголовке `Authorization: Bearer <token>`;
- клиент передаёт идентификаторы товаров и количество товаров при создании заказа;
- клиент передаёт команду отмены собственного заказа;
- сотрудник передаёт команды принятия и завершения заказа, а также данные для создания и изменения товаров каталога;
- сервер читает и сохраняет данные в PostgreSQL;
- PostgreSQL не доступна напрямую пользователям и HTTP-клиентам.

Внешние сервисы не используются. Онлайн-оплата, доставка, уведомления, промокоды, бонусные программы, внешние CRM-системы и другие интеграции не входят в границы продукта.

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- Регистрация пользователя и вход в сервис.
- Определение сервером роли текущего пользователя: `Customer` или `Employee`.
- Просмотр клиентом доступных товаров каталога.
- Создание клиентом заказа из одной или нескольких позиций каталога.
- Серверный расчёт итоговой стоимости по актуальным ценам каталога.
- Сохранение цены товара в позиции заказа на момент его создания.
- Присвоение новому заказу статуса `Created` и связи заказа с текущим клиентом.
- Просмотр клиентом только собственных заказов и их статусов.
- Отмена клиентом только собственного заказа в статусе `Created` с переводом в статус `Cancelled`.
- Просмотр сотрудником заказов в статусе `Created`.
- Принятие сотрудником заказа в работу с переводом в статус `Processing` и назначением ответственного сотрудника.
- Завершение заказа только назначенным сотрудником с переводом из `Processing` в `Completed`.
- Создание сотрудником товаров, изменение их названия, описания, цены и доступности.
- Серверная проверка прав роли, принадлежности заказа клиенту или сотруднику и допустимости переходов состояний.

**Функции, которые можно исключить при нехватке времени:**

- Отдельный браузерный frontend: API можно демонстрировать через Swagger UI или Postman.
- Поиск, фильтрация, сортировка и пагинация каталога и списка заказов.
- Загрузка изображений товаров.
- Расширенные поля товара, например категории, теги или остатки на складе.
- История всех изменений статуса заказа и аудит действий сотрудников.
- Редактирование профиля пользователя.
- Автоматическая документация расширенного уровня, кроме OpenAPI, которую предоставляет FastAPI.
- Автоматизированный CI/CD и развёртывание на удалённом сервере.

После перехода заказа в статус `Completed` или `Cancelled` его состав, сохранённые цены, итоговая стоимость и статус не изменяются. В продукт не входят онлайн-оплата, доставка, возвраты, промокоды, бонусная программа, автоматические уведомления, внешние интеграции и сложная CRM-функциональность.

## 9. Стек и путь к первой работающей версии

**Основные технологии:**  
Python 3.12, FastAPI для REST API, Pydantic для валидации HTTP-данных, Uvicorn как ASGI-сервер, PostgreSQL как реляционная база данных, SQLAlchemy 2.x для доступа к данным, Alembic для миграций схемы БД, JWT Bearer access token для аутентификации, Argon2 или bcrypt для хеширования паролей, Docker и Docker Compose для локального запуска, pytest и HTTPX для тестирования, Ruff для форматирования и линтинга.

**Технологии, новые для команды:**  
Конкретный набор уточняется после согласования команды. Предполагается углублённое использование FastAPI-зависимостей для аутентификации и контроля ролей, Alembic migrations, контейнеризации через Docker Compose и интеграционных тестов API с PostgreSQL.

**Внешние сервисы, необходимые для запуска:**  
Внешние облачные сервисы не требуются. Для локального запуска необходимы Docker Engine и Docker Compose; PostgreSQL запускается как контейнер в составе проекта. Секреты и параметры подключения передаются через переменные окружения, а файл `.env` с локальными значениями не добавляется в Git.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:**  
Все основные сценарии выполняются локально: FastAPI-приложение и PostgreSQL запускаются через Docker Compose. Запросы к API выполняются через Swagger UI, Postman или HTTP-клиент. Демо-пользователи и товары создаются seed-скриптом или миграцией, поэтому работа продукта не зависит от внешних каталогов, платёжных систем, служб доставки и других удалённых сервисов.

**Что команда реализует первым, чтобы получить запускаемую версию:**  
Команда создаст FastAPI-приложение и конфигурацию Docker Compose с отдельными контейнерами API и PostgreSQL. Затем добавит endpoint `GET /health`, который возвращает успешный статус, и базовую конфигурацию подключения к БД. Первой запускаемой версией считается локально запускаемый сервис, для которого команда может выполнить запрос к `GET /health` и получить успешный ответ.
